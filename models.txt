InsureFlow — Database Models (As Built)
Last Updated: 2026-06-13

NOTE: This file reflects the ACTUAL implementation, which differs from the
original spec in a few intentional ways (documented below).

===========================================
DEVIATIONS FROM ORIGINAL SPEC
===========================================

1. Auth model REMOVED
   → OTP state is embedded directly inside the User document.
   → No separate "auth" collection needed.

2. AddOn model REMOVED (as a separate collection)
   → Add-ons are embedded inside InsurancePlan as EmbeddedAddOn sub-model.
   → Plans with no add-ons have available_add_ons = [].

3. Payment MOVED from main_backend to provider_backend
   → Lives in insureflow_provider database.

4. Quote REDESIGNED
   → Originally: one document per plan per transaction.
   → Now: one document per transaction, with items: List[QuoteItem] inside.

5. Notification NOT YET BUILT
   → Deferred to a later phase (low priority).

6. Application model REMOVED
   → Replaced by InsuranceDetail model.
   → Insurance-specific fields will be finalized later.

7. Payment UPDATED
   → Payment model is still in provider_backend.
   → Mock gateway flow now includes payment-OTP verification on the customer's mobile number.
   → Payment model now includes gateway URL and embedded payment OTP state.

8. Company model ADDED in provider_backend
   → Used to register external systems/companies for provider API access.
   → Stores only hashed API keys for secure communication.

9. ProviderUser model ADDED in provider_backend
   → Used for provider-side admin login with email + password + OTP.
   → Separate from company records because companies are not login identities.

--- Model 1: User ---
Collection: "users"
File: user_model.py
One model for both Customer (USER) and Staff (ADMIN).
OTP state is embedded here — no separate Auth collection.

User {
    _id              : ObjectId
    mobile_number    : String          (unique — primary identity for USER and reusable across multiple policy journeys)
    first_name       : String
    last_name        : String
    user_role        : UserRole        (default: USER)
    email            : Optional[EmailStr]  (unique sparse — login identity for ADMIN)
    password         : Optional[String]    (hashed — ADMIN only)
    dob              : Optional[Date]
    address          : Optional[Address]   (embedded sub-model)
    user_metadata    : Optional[dict]
    otp              : Optional[UserOtp]   (embedded — None when no OTP pending)
    is_active        : Boolean         (default: True)
    last_login_at    : Optional[DateTime]
    created_at       : DateTime
    updated_at       : DateTime
}


--- Model 2: Transaction ---
Collection: "transactions"
File: transaction_model.py

Transaction {
    _id              : ObjectId
    transaction_id   : String          (unique, e.g. "TXN-2026-0001"; one new ID per policy purchase journey)
    user_id          : String          (ref → User._id; one user can own many transactions)
    current_status   : TransactionStatus (default: FORM_SUBMITTED)
    status_history   : List[StatusHistoryEntry]
    last_active_at   : DateTime
    selected_plan_id : Optional[String]
    completed_at     : Optional[DateTime]
    created_at       : DateTime
    updated_at       : DateTime
}


--- Model 3: InsuranceDetail ---
Collection: "insurance_details"
File: insurance_detail_model.py
Replaces the old Application model.
This model belongs in main_backend because it stores the customer-side form snapshot for one transaction.
It is the source of truth for resume flow and customer journey continuity.

InsuranceDetail {
    _id                       : ObjectId
    transaction_id            : String          (ref → Transaction.transaction_id)
    user_id                   : String          (ref → User._id)
    insurance_type            : String          ("life" | "health" | "general")

    proposer_first_name       : Optional[String]
    proposer_last_name        : Optional[String]
    proposer_mobile_number    : Optional[String]
    proposer_email            : Optional[String]
    proposer_dob              : Optional[Date]
    proposer_gender           : Optional[String]

    insured_members           : List[dict]      (default: [] for phase 1 flexibility)
    sum_insured_requested     : Optional[Float]
    policy_term_years         : Optional[Integer]
    premium_preference        : Optional[String]

    occupation                : Optional[String]
    annual_income             : Optional[Float]
    city                      : Optional[String]
    state                     : Optional[String]
    postal_code               : Optional[String]

    existing_insurance_details: Optional[dict]
    medical_history           : Optional[dict]
    additional_answers        : Optional[dict]

    form_step                 : Optional[String]   (tracks where the customer stopped)
    is_form_completed         : Boolean            (default: False)
    created_at                : DateTime
    updated_at                : DateTime
}

===========================================
RELATIONSHIPS
===========================================

USER (role=USER)
 |-- 1:Many --> TRANSACTION (user_id)
 |                |-- one mobile-number user can create multiple separate transactions
 |                |-- 1:1 --> INSURANCE DETAIL (transaction_id, user_id)
 |                |-- 1:1 --> QUOTE (transaction_id) [provider backend]
 |                |             |-- items[]: List[QuoteItem]
 |                |                           |-- selected_add_ons: List[SelectedAddOn]
 |                |-- 1:1 --> PAYMENT (transaction_id, user_id) [provider backend]
 |                |             |-- mock gateway URL + payment OTP flow (planned behavior)
 |                |-- 1:1 --> POLICY (transaction_id, user_id)
 |                |             |-- add_ons: List[PolicyAddOn] (embedded)
 |                |-- 1:Many --> TICKET (transaction_id, user_id)

Journey Resume Rule:
  Returning users log in again using mobile OTP and continue from the latest incomplete transaction.
  Login OTP and payment OTP are separate flows, even when both are sent to the same mobile number.

USER (role=ADMIN)
 |-- handles --> TICKET (admin_id)
 |-- registers --> COMPANY (provider backend access)

PROVIDER USER (role=ADMIN)
 |-- logs in to --> Provider Admin Frontend
 |-- manages --> COMPANY
 |-- manages --> INSURANCE PLAN
 |-- monitors --> QUOTE
 |-- monitors --> PAYMENT

COMPANY
 |-- represents --> Insurance provider company OR mid-app client (e.g. InsureFlow)
 |-- authenticates --> provider backend APIs using API key

INSURANCE PLAN (standalone)
 |-- available_add_ons: List[EmbeddedAddOn] (embedded)
 |-- referenced in --> QuoteItem.plan_id

Cross-Backend Link:
  Main Backend (Transaction.transaction_id) <---> Provider Backend (Quote.transaction_id)
  Connected via transaction_id (String), not ObjectId.
  Payment records are also linked by transaction_id and user_id in provider_backend.

DATABASE SETUP
===========================================

MongoDB Atlas — single cluster, two databases:

  insureflow_main (main_backend)
   |-- users
   |-- transactions
   |-- insurance_details
   |-- policies
   |-- tickets
   |-- notifications  <- not yet built

  insureflow_provider (provider_backend)
   |-- companies
   |-- insurance_plans
   |-- quotes
   |-- payments
   |-- provider_users
